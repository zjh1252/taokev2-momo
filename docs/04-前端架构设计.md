## 3. 路由域与渲染策略

前端页面分为三个路由域（Route Group），各有不同的渲染策略和布局：

### 3.1 `(public)` — 公开域

- **渲染策略**：Server Component 优先，全链路 SSR
- **SEO**：完整支持 — `generateMetadata`、JSON-LD 结构化数据、`hreflang`
- **布局**：AppHeader + 内容 + AppFooter
- **数据获取**：页面级 `async` 函数直接 fetch，数据在服务端拼好 HTML
- **交互组件**：仅在叶子节点标记 `'use client'`（如筛选器、收藏按钮），保持最小客户端 JS
- **页面示例**：首页、课程列表/详情、讲师列表/详情、文章、案例

### 3.2 `(auth)` — 认证域

- **渲染策略**：表单交互为主，组件使用 `'use client'`
- **SEO**：不需要（不设置 `generateMetadata`，或设置 `robots: noindex`）
- **布局**：极简居中卡片，仅显示 Logo
- **页面示例**：登录、注册、忘记密码

### 3.3 `(portal)` — 登录后域

- **渲染策略**：布局层（Layout / Header / Footer）走 Server Component；页面内容按需使用 `'use client'`
- **SEO**：不需要（`robots: noindex`）
- **布局**：与 `(public)` 共享 AppHeader + AppFooter（同一组件，两处引用）
- **鉴权**：`(portal)/layout.tsx` 中执行 AuthGuard，未登录 redirect 到 login
- **数据获取**：首屏可服务端预取权限/用户信息，交互部分走客户端请求
- **页面示例**：用户中心、我的课程、订单、证书、课程管理

### 3.4 布局共享关系

```text
(public)/layout.tsx   → 引用 AppHeader + AppFooter
(portal)/layout.tsx   → 引用 AppHeader + AppFooter（同一组件） + AuthGuard
(auth)/layout.tsx     → 独立极简布局
```

AppHeader 内部通过服务端读取 session 判断登录状态，显示"登录按钮"或"用户头像下拉"，仅下拉菜单为 `'use client'`。

## 4. 国际化（i18n）规范

### 4.1 架构分层

- **`i18n/`**：国际化引擎配置（如何加载、如何路由、如何导航）
- **`messages/`**：翻译数据（`<locale>/<namespace>.json`）

两者职责不同，不可混淆。

### 4.2 翻译调用规则

| 组件类型 | 使用方式 | 说明 |
|----------|----------|------|
| `async` Server Component（page/layout） | `getTranslations('namespace')` | 从 `next-intl/server` 导入 |
| 非 async 组件（无 `'use client'`） | `useTranslations('namespace')` | 默认仍为 Server Component，服务端执行 |
| Client Component（有 `'use client'`） | `useTranslations('namespace')` | 通过 `NextIntlClientProvider` 获取 messages |
| `components/ui/` 通用 UI 组件 | **禁止调用翻译**，通过 props 接收文案 | UI 组件不绑定业务语义 |

### 4.3 不做二次封装

直接使用 `useTranslations(namespace)` 和 `getTranslations(namespace)`，不封装 `useT()` / `getT()` 等 wrapper。理由：
- next-intl v4 提供完整的类型安全（key 补全、参数校验）
- wrapper 会将 key 退化为 `string`，丢失所有类型信息
- namespace 隔离本身就是 next-intl 的设计意图

### 4.4 messages 组织

```text
messages/
  zh-CN/
    common.json          # 通用文案（保存、取消、确认、加载中等）
    nav.json             # 导航文案
    auth.json            # 登录/注册
    course.json          # 课程相关
    user.json            # 用户中心
    ...
  en/
    common.json
    nav.json
    auth.json
    course.json
    user.json
    ...
```

namespace 命名与 `modules/` 目录名对齐：`modules/course` 对应 `course.json`，使用 `useTranslations('course')`。

### 4.5 locale 策略

- 默认 locale：`zh-CN`
- 支持 locale：`zh-CN`、`en`（后续可扩展 `zh-HK`、`zh-TW`）
- URL 策略：`localePrefix: 'as-needed'`（默认语言不显示前缀）
- 导航封装：统一使用 `i18n/navigation.ts` 导出的 `Link` / `useRouter` / `redirect`，不直接使用 `next/navigation`

## 5. 模块化与防腐层

### 5.1 modules 目录职责

每个业务域在 `modules/` 下独立管理：

```text
modules/<domain>/
  api/              # 后端接口请求（fetch 封装调用）
  components/       # 该域的业务 UI 组件
  services/         # DTO → 领域模型转换
  types/            # 该域的前端类型定义
```

### 5.2 防腐层原则

- 后端 API 调用统一放在 `modules/<domain>/api/`
- DTO 到前端领域模型的映射放在 `modules/<domain>/services/`
- 页面和组件只消费前端领域模型，不直接依赖后端原始字段
- 后端返回结构变更时，只需修改 `services/` 中的映射，不影响 UI 层

### 5.3 Server / Client API 区分

同一个模块内，按数据获取场景区分：

```text
modules/course/api/
  queries.ts          # Server 侧数据获取（SSR 页面使用）
  mutations.ts        # Client 侧操作（表单提交、状态变更）
```

## 6. 基础设施层

### 6.1 lib/ 职责

技术基础设施，与业务无关，可跨项目复用：

| 路径 | 职责 |
|------|------|
| `lib/utils.ts` | `cn()` 等基础工具（shadcn 依赖） |
| `lib/format.ts` | 日期、金额、时长格式化 |
| `lib/storage.ts` | localStorage 封装 |
| `lib/http/client.ts` | API 客户端：fetch 封装、拦截器、token 自动注入、401 刷新重试 |
| `lib/auth/session.ts` | 服务端 session/cookie 读取 |
| `lib/env/` | 环境变量集中读取与校验 |
| `lib/permission/` | RBAC 权限判断工具 |

### 6.2 config/ 职责

编译时确定的、与运行环境无关的应用级常量：

| 路径 | 职责 |
|------|------|
| `config/site.ts` | 站点名称、描述、SEO 默认值 |
| `config/routes.ts` | 路由路径常量（避免硬编码） |
| `config/constants.ts` | 业务常量（分页默认值、角色枚举、文件大小限制等） |

### 6.3 types/ 职责

仅放全局共享类型声明。业务类型跟着 `modules/<domain>/types/` 走。

| 路径 | 职责 |
|------|------|
| `types/global.d.ts` | 全局类型声明（Window 扩展等） |
| `types/api.d.ts` | 通用 API 响应结构（`ApiResponse<T>`、`PageResponse<T>`） |

## 7. 环境变量管理

### 7.1 文件分层

| 文件 | 用途 | 是否提交 |
|------|------|----------|
| `.env.example` | 变量模板，新成员参考 | 是 |
| `.env.local` | 本地开发私有值 | 否 |
| `.env.development` | 开发环境默认值 | 是 |
| `.env.production` | 生产构建默认值（敏感值由 CI 注入） | 视情况 |

### 7.2 命名约束

- 前端可暴露变量统一使用 `NEXT_PUBLIC_` 前缀
- 密钥/密码等敏感值禁止使用 `NEXT_PUBLIC_` 前缀
- 常用变量：`NEXT_PUBLIC_API_BASE_URL`、`NEXT_PUBLIC_CDN_BASE_URL`、`NEXT_PUBLIC_APP_ENV`

### 7.3 读取方式

通过 `lib/env/` 集中读取与校验，应用启动时 fail-fast，缺少必填变量直接报错。页面和组件不直接读取 `process.env.*`。

## 8. 包管理器规范

- 统一使用 **pnpm**
- 锁文件仅保留 `pnpm-lock.yaml`，禁止混用 `package-lock.json` / `yarn.lock`
- 文档、CI、脚本中命令统一使用 `pnpm`（`pnpm install`、`pnpm dev`、`pnpm build`）
- 建议在 `package.json` 中配置 `packageManager` 字段（Corepack）与 `engines.node`

## 9. 组件设计原则

### 9.1 `components/ui/`

- shadcn 自动生成的基础 UI 组件
- 不包含业务逻辑，不调用 `useTranslations`
- 文案通过 props 传入

### 9.2 `components/shared/`

- 跨模块复用的业务组件（如通用分页、状态页、加载指示器）
- 可调用 `useTranslations`（使用 `common` namespace）

### 9.3 `components/layout/`

- 布局组件：AppHeader、AppFooter、UserDropdown 等
- AppHeader / AppFooter 为 Server Component，被 `(public)` 和 `(portal)` layout 共同引用
- 仅交互叶子组件（如 UserDropdown）标记 `'use client'`

### 9.4 `modules/<domain>/components/`

- 该业务域专属的 UI 组件
- 可调用 `useTranslations` 使用对应域的 namespace
- Server / Client 按需标记，默认不加 `'use client'`

## 10. `'use client'` 使用原则

1. **默认不加**：组件默认是 Server Component，只有需要 `useState`、`useEffect`、事件处理器时才加
2. **推到叶子**：`'use client'` 具有感染性（子组件全部变客户端），所以尽量在最小的叶子组件标记
3. **布局不加**：layout.tsx 保持 Server Component，确保 Header/Footer 服务端渲染
4. **整页不加**：不在 page.tsx 级别标记 `'use client'`，而是把交互部分拆成独立的 Client Component 嵌入
