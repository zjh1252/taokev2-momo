# C 端本地响应时间优化设计

## 背景

C 端（`frontend`）在本地开发环境（`pnpm dev` + 本地/远程后端）整体体感慢：白屏、数据晚到、交互卡顿均有可能，但尚未定位主因。仓库内无既有性能专项文档；后端与部分前端路径已有 N+1 / `Promise.all` / `revalidate` 等局部优化，但首页等路径仍存在「列表后再逐条拉详情」等可能放大延迟的模式。

## 目标与范围

### 目标

降低 C 端本地开发时的「打开慢 / 数据晚到」体感；以可测量证据驱动改动，不做无证据的大重构。

### 范围

- **主战场**：`frontend`
- **可扩展**：若摸底证明某后端 API 是主因，定点修改对应后端接口
- **不包含**：admin-frontend、taoke-uniapp、全站架构重写

### 非目标

- 不把「仅 `next dev` 冷编译慢」误当成业务性能问题去大改业务代码
- 不引入新的全站状态管理 / 请求框架，除非摸底证明现有模式是瓶颈且改动面可控

### 成功标准（本地）

摸底后选出的 Top 1–3 热点页面，首屏可用时间或关键 SSR/API 耗时有可对比的下降（改前/改后各记一笔）。

## 方案选择

采用 **先摸底，再修 Top 瓶颈**（方案 A），不采用全量数据层改造或纯开发体验改造作为主路径。

若摸底结论主要是 `next dev` 编译慢，可叠加轻量开发体验止血（如评估 Turbopack），但不替代业务热点修复。

## 摸底方法

### 样本页（固定）

1. 首页
2. 一个高频列表页（专家列表或公开课列表）
3. 一个详情页（专家详情或课程详情）

### 每次记录三类时间

| 指标 | 含义 |
|------|------|
| Next 编译 / 路由就绪 | `pnpm dev` 自身成本 |
| 文档 / HTML 到达（TTFB） | SSR 或文档响应 |
| Network Top 慢 API | 含是否串行瀑布 |

### 主因标签（可多选）

- `dev 编译`
- `SSR 瀑布流`
- `单接口慢`
- `前端重渲染`

## 优化策略

| 主因 | 优先手段 |
|------|----------|
| SSR 瀑布 / 多余详情请求 | 并行 `Promise.all`、列表字段一次返回、去掉「列表后再逐条详情」 |
| 单接口慢 | 定点查后端 N+1 / 缺索引 / 过重 DTO，只改该接口 |
| 首屏被次要区块堵住 | Suspense 拆分：壳先出，次要区块后流式 |
| 主要是 `next dev` | 轻量开发体验止血；业务代码少动 |

### 已知可疑热点（待基线证实后再改）

首页 `load-home-data.ts` 中存在对公开课等「列表后再 `getCourseDetail` 补封面」的模式；若基线显示其在关键路径上，优先止血。

### 约束

- 每轮最多修 Top 1–3
- 改前改后用同一套样本、尽量同条件对比
- 不顺手做无关重构

## 落地步骤

1. **基线**：对三个样本页各记一笔本地耗时（编译 / TTFB / Top API）
2. **归因**：为每个样本页打主因标签
3. **止血**：按优先级改 Top 1–3
4. **复测**：同一环境、同一操作路径对比基线
5. **收口**：记录基线、改动点、前后对比；若剩余主要是 `next dev`，单列后续可选项，本轮不强行大改

## 验收

- 有改前/改后数字，不是主观「感觉快了」
- 每条优化对应摸底证据
- 样本页内容与交互无功能回归

## 风险

- 本地数字受机器负载、后端是否已启动、冷/热编译影响 → 对比时尽量同条件
- 修前端瀑布后若后端仍慢，需第二轮定点后端，本轮不无限扩大范围
